# Ethics

> Research prototype only. Not medical advice, diagnosis, treatment, or a medical device.

## What this project is

A reliability framework and audit pipeline for wearable-derived physiological signals. It produces a per-cohort and per-participant report describing how trustworthy a set of measurements is, broken down by acquisition quality, artifact burden, temporal stability, missingness pattern, device bias, and confounding risk.

## What this project is not

It is not a diagnostic tool. It does not predict disease, recommend medical action, or trigger alerts to a person or their clinician. It does not produce labels that should be interpreted as medical findings. The word "patient" does not appear in our outputs; we use "participant" because the framework is for research data analysis, not care delivery.

## Why a non-clinical framing matters

The wearable space has a recurring failure mode: a research prototype shows interesting results on a clean dataset, gets surfaced in a press release, and is then used informally to make claims about a clinical population. We want this project to be unusable for that pipeline. The disclaimer text is therefore not boilerplate. It is repeated on every output because we expect outputs to be passed around independently of the codebase.

## Bias considerations

The synthetic generator includes a skin-tone proxy that applies a documented penalty to PPG signal quality. We added this because real PPG measurements show systematic differences by skin pigmentation, and a framework for auditing wearable reliability would be incomplete without a way to demonstrate, on synthetic data, what the audit machinery does in the presence of such an effect. The choice has two implications:

1. The bundled models have not been audited for fairness across the skin-tone-proxy axis. Anyone using this framework on real data should run that audit; the figures and tables to do so are already in the codebase.
2. We do not claim that the magnitude of the simulated effect (0.12 × proxy on PPG SQI) corresponds to any real-world device. It is large enough to be detectable by the framework and small enough not to dominate other effects. Treat the number as a worked example, not a calibration.

Device bias is similar. We simulate three device families with documented offsets. The offsets are illustrative, not calibrations of any real product line.

## Participant data

This repository contains no participant data, identifiable or otherwise. All data is generated by `src/data/synthetic_signal_generator.py`. Any researcher applying this toolkit to real data is responsible for the data-handling obligations that come with that data, including any applicable IRB approval, informed consent, data-use agreements, and storage controls.

## Recommendations to downstream users

If you use this toolkit on real wearable data, we ask that you:

- Run the full audit pipeline before doing any modeling. Treat the audit report as a precondition, not a postscript.
- Report the trust-score components for your cohort, not just the overall number. The decomposition is the point.
- Run sensitivity analyses for any metric whose `confounding_risk` component falls below ~70. Re-run with the confounder included as a covariate and report whether your finding survives.
- Run a stratified audit by device type before pooling across devices.
- If you have a fairness-sensitive variable (skin tone, age, sex, geography), run a stratified audit by that variable and publish the per-stratum trust scores even if your headline number is fine.

## Recommendations to reviewers

If you are reviewing a paper that uses this toolkit, the questions to ask are:

- Were the audit components reported individually?
- Did the authors stratify by device type?
- Did the authors stratify by the relevant fairness axes for their cohort?
- For each confounding risk above the configured threshold, was a sensitivity analysis performed?

The audit pipeline is designed to make answers to all four questions easy to produce. Absence of any of them is a meaningful signal.

## Limits we acknowledge

The audit pipeline cannot detect failure modes that the synthetic generator does not include. Notable omissions:

- Firmware version drift mid-study.
- Manufacturer pipeline changes (e.g., a smartwatch quietly switching its HR algorithm in a software update).
- Adversarial behavior by participants (faking data, sharing devices).
- Cultural and contextual factors (shift work, religious practices) that change wear patterns in ways our simple state-dependent missingness model does not capture.

We list these explicitly because the audit's claim is bounded. It is a useful first-pass check. It is not a substitute for the kind of validation that real clinical deployment requires.
